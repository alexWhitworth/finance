  where _nav_product_oracle (line 169) = initial_nav * (1 + return_series).prod()

  any intermediate backtest state. This is logically independent only if
  return_series and nav_series are independently computed.

    - port_return is computed at line 112: _compute_port_return(nav_before, state.prev_total_nav)

  DOES make it partially tautological: prod(nav_t / nav_{t-1}) = nav[-1] / nav[0]

[ADVISORY — F-017-A1]
  File: tests/test_backtest_integration.py, lines 167–207
  Category: Oracle semi-tautology in zero-contribution variant

  The zero-contribution oracle (line 203) computes:
    oracle = initial_nav * (1 + result.return_series).prod()
  and then asserts:
    result.nav_series.iloc[-1] == pytest.approx(oracle, rel=1e-9)

  Since return_series[t] = nav_before_t / prev_total_nav_t - 1 and nav_series[t]
  = total_nav_t (which equals nav_before_t when contribution=0.0), the product
  telescopes to nav[-1] / nav[0] = nav[-1] / initial_nav, making the oracle
  algebraically equivalent to nav_series[-1] == nav_series[-1]. The test CANNOT
  fail from a step-function bug that consistently corrupts BOTH nav_series and
  return_series by the same multiplicative factor.

  Partial mitigation exists: the test WOULD catch bugs where nav_series and
  return_series diverge (e.g., a step that mutates nav but not the port_return
  computation path, or vice versa). However, coordinated bugs — such as a
  wrong contribution being baked into both nav and return simultaneously —
  would be invisible.

  Severity: ADVISORY, not BLOCKING. The spec's F-018 same-day consistency test
  provides a truly independent oracle (nav[t] == nav[t-1]*(1+r[t]) + contrib_t
  verified externally from the return series), which closes the gap. F-017
  serves as a smoke test for internal consistency of the (nav, return) pair;
  F-018 provides the independent accounting proof.

  Recommended fix: Document the telescoping identity limitation in the test
  docstring so future readers understand what this test does and does not prove.
  Optionally add one reference NAV computation using raw asset returns directly
  (bypassing the backtest's return_series) for the no_gtt_no_leaps case:
    reference_nav = initial_nav * (1 + rd.returns["VTI"] * w_VTI + ...).prod()
  This would provide a truly external oracle for at least one config variant.

[ADVISORY — F-017-A2]
  File: tests/test_backtest_integration.py, lines 270–304
  Category: Double-count guard is heuristic, not a hard constraint

  The AC-2 criterion "Test fails if any step function introduces a contribution
  that appears in return_series (double-count)" is implemented via:
    assert float(month_end_rets.max()) < 10 * median_abs
  (a 10× spike threshold, lines 301–303)

  This is an indirect heuristic detector. It would miss double-counting if:
  (a) contributions are small relative to normal market volatility (the 10×
      threshold may not trigger), or
  (b) the contribution amount is exactly offset by a negative market return on
      the same day.

  The MONTHLY_CONTRIB is $2,000 on a $500,000 NAV (0.4%), well within normal
  daily move amplitudes (~0.7–1.5% σ for a diversified portfolio). A bug where
  $2,000 is added to nav_before before computing port_return would produce only
  ~0.4% spike — easily within the 10× median tolerance.

  A direct guard would be: run two backtests with contribution=0 and
  contribution=C, and assert return_series is IDENTICAL (numpy.allclose) on
  all non-month-end days and DIFFERS by no more than 0 on month-end days
  (since a correct implementation computes return before applying the contribution).

  The existing F-018 test_i2_exact_gtt_no_leaps_all_days provides a stronger
  guarantee for the GTT no-LEAPS config, but not for all 4 configs.

  Severity: ADVISORY. The spec's intent is partially met; the direct guard
  approach would provide stronger AC-2 coverage.

[ADVISORY — F-017-A3]
  File: tests/test_backtest_integration.py, lines 155–163 (comments) and
        spec.json F-017 accounting_oracle field
  Category: Spec oracle not fully implemented for contribution variant

  The spec's accounting_oracle states:
    "nav[-1] == initial_nav * prod(1 + return_series) + sum(monthly_contribution
     for each month_end_date in backtest)"

  The non-zero contribution variant does NOT implement this full oracle.
  Instead, the test verifies only:
    "nav_with_contrib > nav_without_contrib"  (test_contrib_nav_exceeds_zero_contrib)
  and a heuristic double-count guard (test_double_count_guard).

  The comments at lines 157–163 acknowledge this:
    "For a non-zero contribution backtest the arithmetic oracle is more involved
     because each contribution compounds forward."

  This is accurate — the spec oracle is actually incorrect for any positive-return
  backtest because each contribution earns returns after the contribution date
  (it compounds forward, so nav[-1] > initial_nav * prod + sum of undiscounted
  contributions). The F-018 per-day oracle is the correct formulation.

  The spec oracle "nav[-1] == initial_nav * prod(1+r) + sum(contributions)" is
  only exact if contributions are deposited AT THE END (no compounding). In the
  actual implementation, contributions are deposited at month-end and then earn
  returns for the remaining days — so nav[-1] > the spec oracle for positive-
  return backtests. The Actor correctly recognized this and used the weaker bound.

  Impact: The spec's accounting_oracle for the contribution variant is incorrect
  as written. The Actor's structural bound (contrib nav > zero-contrib nav) is
  correct but weaker than the spec implies. This is an ESCALATION for the spec
  owner to decide whether to: (a) accept the weaker bound as sufficient given
  F-018 covers the per-day invariant, or (b) implement the corrected oracle
  sum_t(contrib_t * prod(1+r, t+1 to T)) which is the exact present-value chain.

  Severity: ADVISORY for the Actor (implementation is defensible). ESCALATION
  note for spec owner regarding the oracle formula correctness.

[ESCALATION — E1]
  Category: Spec accounting_oracle for contribution variant is incorrect
  The oracle "nav[-1] == initial_nav * prod(1+r) + sum(contributions)" does not
  account for compounding of contributions. The correct oracle is:
    nav[-1] == initial_nav * prod_t(1+r_t) +
               sum over month-end dates s: contrib * prod_{t=s+1}^{T}(1+r_t)
  The Actor correctly declined to implement the erroneous oracle and fell back
  to a structural bound. The spec owner should update the F-017 accounting_oracle
  field to either (a) reference F-018 for the per-day formulation, or (b)
  provide the corrected telescoping oracle for the contribution case.
