SUMMARY
================================================================================

F-020 (Bug 3 fix: _apply_contribution drops leaps_monthly on Long month-ends) is
substantially correct — it fixes the bug, passes all applicable tests, and satisfies
the I2 invariant. However, the implementation DEVIATES from the spec's stated
acceptance criteria and accounting oracle on a single but literal point: on Long
month-end days the Actor credits leaps_VALUE instead of leaps_POOL.

The deviation is architecturally defensible (leaps_value is in the NAV formula, so
I2 is satisfied), but it contradicts: (1) the text of AC-1, (2) the text of AC-2
label/intent, (3) the F-020 accounting_oracle field, (4) the "single-line change"
description in F-020, and (5) the edge case 2 text. One test that should cover edge
case 2 (gtt_active=False + use_leaps=True contribution path) is entirely absent.

FINDINGS
================================================================================

[ADVISORY] src/finance/_backtest_steps.py:811-815 — The spec F-020 description
says "add leaps_monthly to leaps_pool unconditionally" and the acceptance criteria
say "leaps_pool_out == leaps_pool_in + leaps_monthly" for Long month-ends. The
implementation instead branches: regime_t==0 -> leaps_pool, regime_t==1 ->
leaps_value. This is a LITERAL spec deviation on AC-1. The NAV I2 invariant is
still satisfied because leaps_value is included in total_nav (same formula). The
Actor's docstring comment ("On Long days: credit leaps_value directly — contracts
already purchased by run_leaps_simulation; this makes NAV reflect the cash inflow")
provides a coherent economic rationale for the deviation.

Architectural consequence: by routing Long-day LEAPS contribution to leaps_value
instead of leaps_pool, the Actor avoids a potential double-count at re-entry
(_apply_gtt_reentry uses leaps_pool in its rebalance total). If leaps_monthly were
added to leaps_pool on Long days, it would be swept into the rebalance total on
re-entry — that may or may not be the correct economic treatment depending on spec
intent. The Actor's choice is at least internally consistent with how re-entry math
works. This merits confirmation from the spec author before being marked a hard
failure.

[ADVISORY] tests/test_backtest_steps.py:1239-1287 — Edge case 2 ("GTT inactive
(gtt_active=False) but use_leaps=True: leaps_pool still receives leaps_monthly on
month-end") is NOT TESTED. The spec explicitly calls this out in the edge_cases
array. The implementation routes no-GTT Long days (regime_t=1) to leaps_value, so
if the spec intent is leaps_pool, this edge case is both untested AND silently
violated. A test for gtt_active=False + use_leaps=True + regime_t=1 contribution
would immediately expose the deviation.

[ADVISORY] tests/test_backtest_integration.py:402 — The F-018 Scenario B test for
GTT+LEAPS deliberately uses a WEAKER bound ("implied delta > 0 on month-ends")
instead of the exact I2 oracle. This is documented in the test ("weaker but still
tight bound") but means it does NOT directly verify that the exact leaps_monthly
dollar amount flows through on Long month-ends. A tighter test asserting
implied_delta == monthly_contribution within 1e-6 on Long month-ends would
provide definitive verification of AC-1/AC-4.

[ADVISORY] tests/test_backtest_steps.py:1253 — The AC-1 test name says
"credits_leaps_value" but the spec says leaps_POOL. The test name accurately
describes the implementation but the test name misaligns with the spec language.
This is a traceability gap.
