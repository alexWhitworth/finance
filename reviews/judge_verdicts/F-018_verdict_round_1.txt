FINDING-1 [ADVISORY] — Oracle tautology in test_i2_exact_gtt_no_leaps_all_days
and test_i2_contrib_delta_nonneg_gtt_leaps_all_days

  File: tests/test_backtest_integration.py:360-453

  Both "I2 oracle" tests derive their expected value from backtest outputs:

    expected = nav.iloc[i-1] * (1 + rets.iloc[i]) + contrib

  where nav.iloc[i-1] is previous-day backtest output and rets.iloc[i] is
  current-day backtest output. This is algebraically guaranteed to hold
  by the production code's accounting identity:

    port_return[t] = nav_before / prev_total_nav - 1          [portfolio.py:112]
    nav[t] = nav_before + contribution                         [portfolio.py:116-118]

  Because _advance_state sets state.prev_total_nav = total_nav[t-1], the
  test oracle reduces to: nav[t] = (nav[t-1] * (nav_before/nav[t-1])) + contrib
                                  = nav_before + contrib = nav[t]

  The identity holds by construction for any backtest that uses this formula,
  regardless of whether nav_before itself is computed correctly. A global scale
  error, a wrong initial_nav, or a systematic bias in holdings compounding would
  all pass this test undetected because the error would appear proportionally in
  both nav_series and return_series.

  Evidence: test actually achieves differences of ~1e-11 to 1e-15 (floating-point
  noise only), not meaningful numerical error. The 1e-9 tolerance is academic.

  The test does provide value as a structural sanity check that the backtest
  pipeline is internally consistent, but it cannot detect absolute errors in the
  NAV accounting.

  Recommended fix: Replace nav.iloc[i-1] with an independent accumulator seeded
  from initial_nav, compounding each day using the asset returns from return_data
  (the INPUT, not the backtest output). This would make the oracle externally
  independent, able to catch wrong initial capital deployment, wrong contribution
  application, or wrong return compounding. This is a test strengthening task,
  not a production code bug.

FINDING-2 [ADVISORY] — Spec edge case "Month-end re-entry day" is not exercised;
TestSameDayConsistency docstring claim is factually incorrect

  File: tests/test_backtest_integration.py:357, 356-401
  Spec: features[F-018].edge_cases[0]

  The F-018 spec explicitly lists as a required edge case:
    "Month-end re-entry day: contribution_on_t = monthly_contribution
     (both base and LEAPS shares)"

  The F-018 corpus (mask[100:200]=0, re-entry at idx=200) places re-entry on
  2018-10-10, which is NOT a month-end. The last business day of October 2018
  is at idx=215 (2018-10-31), 15 days after re-entry.

  The TestSameDayConsistency class docstring at line 357 claims:
    "Covers 504 days including: defensive window, re-entry,
     month-end re-entry coincidence."

  This claim is factually incorrect. No month-end+re-entry coincidence exists
  in the F-018 corpus, and neither does one exist in the F-019 corpus
  (F-019 re-entries at 2018-06-06 and 2019-01-02, neither a month-end).

  This edge case is specifically required because the step ordering
  (_apply_gtt_reentry runs before _apply_contribution per portfolio.py:115-113)
  means the rebalance is computed from pre-contribution NAV and the subsequent
  contribution enters at a freshly-deployed portfolio. Without this coincidence,
  the R-004 risk mitigation (Phase 4b verifies R-004) is incomplete.

  Recommended fix (two parts):
  (a) Remove the false claim from the TestSameDayConsistency docstring.
  (b) Add a test that uses a corpus where the defensive window end is positioned
      such that mask switches 0→1 exactly on a month-end trading day. For example,
      shift the window end to align with 2018-10-31 (idx=215).

  Note: this is a test gap, not a production code bug. The production code
  correctly handles this coincidence (R-004 mitigation is the step ordering
  itself); the test just doesn't exercise it.

FINDING-3 [ADVISORY] — Bug 1 regression guard threshold is leaps_fraction-dependent
with marginal safety margin

  File: tests/test_backtest_integration.py:480

  The regression guard threshold is hardcoded to 0.10 (10%). With the test
  config's leaps_fraction=0.15, Bug 1 produces a return spike of ~15.96%,
  giving 5.96pp of headroom above the threshold. The guard works correctly for
  this specific configuration.

  However, the guard's discriminating power scales with leaps_fraction. If a
  future test or config uses leaps_fraction < 0.10, the stale LEAPS spike would
  fall below the 10% threshold and go undetected. The threshold is not documented
  as dependent on leaps_fraction, creating silent failure modes under config
  changes.

  Additionally, the test comment states it checks |return[reentry]| against 0.10
  but the docstring says "we verify by checking that the re-entry day's return is
  bounded (|r[reentry]| < 0.10)". The threshold 0.10 is not derived from any
  first-principles calculation — it is an empirically chosen value that happens to
  work for 15% LEAPS.

  Recommended fix: Document in the test that the threshold (0.10) must exceed the
  leaps_fraction (currently 0.15 → spike of ~15%). Assert explicitly that the
  corpus config's leaps_fraction > 0.10, so the threshold remains valid. Better:
  compute the expected spike magnitude and assert the threshold is set to half
  of it (0.15/2 = 0.075 would be safer).
