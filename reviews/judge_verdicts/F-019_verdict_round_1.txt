FINDING-1 [ADVISORY] — Spec Edge Case R4 Interaction Not Exercised
  File: tests/test_backtest_integration.py, lines 505–509 (corpus spec comment)
  Spec says: "Second re-entry coincides with month-end — tests R4 interaction"
  Reality: re-entry 2 is index 260 = 2019-01-02 (Wednesday, first trading day
  of January 2019). This is NOT a month-end.
  Root cause: The corpus uses pd.bdate_range which does NOT skip public holidays.
  2019-01-01 (New Year's Day) is included as a synthetic trading day at index 259,
  which is the last defensive day. The re-entry falls on 2019-01-02 instead of
  the intended month-end. December 31 2018 (a real month-end) is at index 258,
  which is inside the defensive window.
  Impact: The R4 interaction (re-entry coinciding with month-end, where a
  contribution would normally be deposited) is NOT stress-tested. This edge
  case could hide a contribution-on-re-entry-day accounting error.
  Severity: ADVISORY (tests still pass; the stated behavior is correct for the
  corpus as constructed, but the corpus does not match the spec's stated edge case)

FINDING-2 [ADVISORY] — Boundary Condition in I3 Check Uses Strict Less-Than
  File: tests/test_backtest_integration.py, line 585
  Code: frozenset(c for c in ledger.contracts if pd.Timestamp(c.purchase_date) < reentry1_date)
  The strict < means a contract purchased ON reentry1_date (2018-06-06) is NOT
  classified as a window-1 contract. One such contract exists in the ledger
  (purchased 2018-06-06, also in gtt_close_events with close_date=2018-10-09).
  This is CORRECT behavior: the re-entry day's new contract is a window-2
  contract, not a window-1 contract. The < boundary is semantically right.
  However: that same contract IS in gtt_close_events (closed at second
  defensive window start 2018-10-09). If someone introduced a bug where
  re-entry-day contracts were incorrectly classified as window-1 contracts,
  the test would not catch it. This is a theoretical gap, not a real bug.
  Severity: ADVISORY (no code change needed; add a comment clarifying the
  boundary semantics would be sufficient)

FINDING-3 [BLOCKING — PRE-EXISTING, UNRELATED TO F-019] — Failing Test in Suite
  File: tests/test_gtt_backtest.py, line 859
  Test: test_reentry_creation_iv_matches_mtm_iv_no_gap
  Failure: LEAPS weight at re-entry = 0.5202 but expected 0.50 ± 1e-6.
  This test checks that freshly created re-entry contracts are priced at
  creation IV (not smoothed IV), so leaps_value == capital_deployed and
  weight == target_fraction exactly. The assertion fails with a 4% deviation
  (0.5202 vs 0.50).
  This is NOT an F-019 test failure, but it IS a real correctness failure in
  the re-entry IV consistency logic that F-019's AC-2 is supposed to stress.
  The fact that F-019's AC-2 (< 0.05 bound) passes while this test fails
  suggests: either (a) the IV gap is small enough to produce a sub-5% return
  spike but still violates the weight identity, or (b) the two tests exercise
  different code paths/configs.
  The failing test uses AccountType.TAX_SHELTERED and leaps_fraction=0.5.
  F-019 uses AccountType.TAXABLE and leaps_fraction=0.15.
  This pre-existing failure must be resolved before declaring the full
  Bug 2 fix complete.

Q: Could NAV numbers pass I3 even with stale contracts being double-counted?
A: No — the test does NOT use NAV as a proxy. It directly calls
   _live_contracts(ledger, d) for each of 90 window-2 dates and computes
   the set intersection with window1_contracts. This is the gold-standard
   direct check. A stale contract appearing in the live set would be caught
   on the date it first appears.

Q: Are the returns plausibly low, or suspiciously low (i.e., corpus too gentle)?
A: The max absolute daily return across all 504 days is 0.029 (2.9%). This is
   consistent with the rng.normal(0.0003, 0.01) daily return distribution.
   The VIX drop from 0.50→0.15 at re-entry is present and would stress Bug 2
   (if it existed). The corpus is not pathologically gentle; it simply does not
   produce large enough organic returns to hit the 5% bound under correct code.

Q: Does window-2 also get checked for window-2 contract leakage into window-3?
A: NOT in the F-019 test. The test only checks window-1 leakage into window-2.
   However, manual inspection confirms window-2 contracts live in window-3 = 0/244
   dates. The absence of a second-isolation test (I3 for window-2 → window-3)
   is a minor gap but not blocking given the 0/244 empirical result.
