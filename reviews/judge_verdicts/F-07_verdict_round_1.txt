A-02  unrate_trade_lag_days parameter is accepted but silently unused
      The function signature accepts `unrate_trade_lag_days` (defaulting to
      GTT_UNRATE_TRADE_LAG_DAYS = 1) but the value is never passed to any pure
      function and is not reflected in the returned GttSignalData.
      The docstring correctly documents this as "retained for API symmetry with
      GttConfig" and explains that the publication lag lives inside
      compute_ue_signal. This is intentional per the spec (compute_ue_signal
      does the re-stamping internally; no per-signal day-count shift parameter
      exists in that function's API). However, a caller who sets
      unrate_trade_lag_days=2 gets no error and no effect — silent no-op.
      The spec does not require a warning or error here; this is a known
      API-symmetry simplification documented in the docstring.
      Recommendation: add a note in the docstring or a mypy-suppressable
      `_ = unrate_trade_lag_days` to make the intentional non-use explicit.
      Severity: advisory.

A-03  Empty-VTI path is tested (empty vti_raw raises), but the test for this
      branch (test_fetch_gtt_empty_vix_raises) actually exercises only the
      VIX-empty branch. There is no dedicated test that confirms an empty VTI
      response raises ValueError. The spec edge cases do not explicitly require
      this test, but the production code (gtt.py:300-304) has the branch.
      Coverage is 100% via the pragma: no cover exclusion so this gap is
      invisible to coverage. Not a FAIL because the VTI-empty raise is
      structurally correct; the gap is a missing negative test only.
      Severity: advisory.

A-04  The slow integration test imports fetch_gtt_signal_data from the top-level
      test namespace but also imports Fred and _first_friday_of_following_month
      with inline `from` statements inside the function body. This is
      stylistically inconsistent with the rest of the test file but is
      functionally correct. Minor.
