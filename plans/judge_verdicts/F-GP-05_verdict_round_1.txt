[ADVISORY — 1] Internal NaN gap handling in rfr_series
The current pattern:
    rfr_series = return_data.risk_free_rate.reindex(idx, method="ffill").fillna(0.0)
In pandas 3.0.5, `reindex(idx, method="ffill")` does NOT forward-fill within-series NaN gaps
when the index keys already exist in the original series. Only new index keys (from reindexing
to a different index) are filled by method="ffill". Internal NaN gaps (e.g., ^IRX missing a
few trading days) pass through unchanged and are then filled with 0.0 via fillna(0.0),
silently substituting 0% risk-free rate.

This is a pre-existing behavior in the codebase (the same pattern exists for the use_leaps
rfr_series at line 445) and is NOT introduced by F-GP-05. However, it could cause subtle
hurdle undercounting if ^IRX has sporadic missing days, since the monthly compounding factor
(1+rfr)^(1/12) would be 1.0 for those days instead of the true rate.

Mitigation: Real-world ^IRX from FRED is rarely gapped. The leading-NaN check catches the
most dangerous case. This is low-probability risk for this use case.

If forward-filling internal gaps is desired, the fix is:
    rfr_series = return_data.risk_free_rate.ffill().reindex(idx, method="ffill").fillna(0.0)
This is a pre-existing design choice, not a regression from F-GP-05.

[ADVISORY — 2] Spec criterion wording vs implementation reachability
The spec states "glide_path_config set and use_leaps=False" as an acceptance criterion.
In practice this path cannot be reached because PortfolioConfig validation requires
floor < leaps_fraction which mandates LEAPS keys. The test documents this tension honestly.
If future use cases drop the LEAPS key requirement while keeping glide_path_config (e.g., a
pure-equity glide path), the current validation will block construction. This is an
ESCALATION-level spec question, not a blocking defect.
