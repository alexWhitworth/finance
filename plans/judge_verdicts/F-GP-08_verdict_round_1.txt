3. FINDINGS
----------------------------------------------------------------

ADVISORY — AC-1: No direct test for LEAPS seed at m=2.0
  File: tests/test_glide_path_gtt_reentry.py (no dedicated test)
  The spec's first acceptance criterion states:
    "Under glide_path_config with m_current=2.0, LEAPS initial_capital ==
     dynamic_targets[leaps_key] * total within 1e-6."
  No test directly asserts leaps_seed == dynamic_targets['VTI_LEAPS'] * total.
  The only indirect evidence is test_gtt_reentry_glide_path_weight_sum_at_m3 (m=3.0),
  which shows sum(base_holdings) / total == expected_base_frac, implying by weight-sum
  conservation that leaps_seed == leaps_frac * total. This is a correct logical chain
  but not a direct assertion at m=2.0.
  Recommended fix: add a dedicated test that constructs state with m=2.0, calls
  _apply_gtt_reentry with use_leaps=False, and asserts that the base_assets weight sum
  covers exactly (1 - dynamic_targets['VTI_LEAPS']) of total (equivalently, verifying
  the residual).

ADVISORY — AC-3: NAV conservation test is incomplete
  File: tests/test_glide_path_gtt_reentry.py::test_gtt_reentry_glide_path_nav_conserved
  The test docstring says "Total NAV (holdings + leaps_value) post-reentry equals
  pre-reentry total within 1e-6" but the assertion only checks:
    sum(new_state.holdings.values()) == base_frac * total
  not the full invariant:
    sum(new_state.holdings.values()) + new_state.leaps_value == total.
  Since use_leaps=False in this test, leaps_value=0 and the LEAPS fraction of NAV is
  "unaccounted" in the assertion. This is an acceptable test-design constraint (no
  LEAPS sim in unit tests), but it means the full NAV conservation invariant is never
  directly verified at the unit test level.
  The weight_sum test at m=3.0 also verifies only holdings (not holdings+leaps_value).
  The spec's accounting oracle "sum(new_holdings.values()) + new_leaps_value == total
  within 1e-6" is not directly proven by any unit test.
  Recommended fix: either (a) add a test with use_leaps=False that checks
  sum(holdings) + leaps_seed (computed separately via compute_glide_target_weights)
  equals total, or (b) note explicitly in test docstrings that NAV conservation is
  verified end-to-end only in the integration test.

ADVISORY — Edge case m == 1.0 not tested
  File: tests/test_glide_path_gtt_reentry.py (no test)
  Spec edge case: "Re-entry at m == 1.0: same as above; VTI allocation == 0.0."
  Tests cover m < 1.0 and m > 1.0 (m=2.0, m=3.0) but not the exact boundary m=1.0.
  At m=1.0 the compute_glide_target_weights function should return original
  target_weights (VTI=0.0). This boundary is not exercised in the GTT re-entry test.
  Recommended fix: add test_gtt_reentry_glide_path_at_m_equals_1 asserting VTI=0.0
  and LEAPS seed = w0 * total.

ADVISORY — Edge case gtt_active=False / no-GTT path not tested in F-GP-08 tests
  File: tests/test_glide_path_gtt_reentry.py (no test)
  Spec edge case: "No GTT (gtt_config=None): _apply_gtt_reentry never called; no change."
  The test test_gtt_reentry_not_fired_when_prev_regime_1 covers a related no-op path
  (prev_regime=1), but not the ctx.gtt_active=False path. These are different code
  paths in the no-op guard:
    if not (ctx.gtt_active and state.prev_regime == 0 and inputs.regime_t == 1):
  Recommended fix: add a test that passes ctx with gtt_active=False and asserts
  state is returned unchanged.

BLOCKING — Integration test missing
  File: tests/test_glide_path_gtt_reentry_integration.py (DOES NOT EXIST)
  Spec test_requirements entry (integration):
    "tests/test_glide_path_gtt_reentry_integration.py: GTT-enabled DRIFT+glide_path
     backtest with a Defensive->Long transition at m > 1.5; assert LEAPS seed weight
     and VTI allocation match compute_glide_target_weights(m) * total within 1e-6."
  This is the only test that exercises the full end-to-end flow through the real
  backtest loop: _apply_contribution sets dynamic_target_weights, then a GTT re-entry
  fires and uses those weights to seed LEAPS and allocate base assets. The unit tests
  bypass the backtest loop and construct BacktestContext/PortfolioState manually.
  Without an integration test, the following risks are not exercised:
    - Correct m value at re-entry matches hurdle_contributed accumulated by
      _apply_contribution (R-GP-06).
    - VTI dynamic allocation is consistent with glide-path state at re-entry.
    - No drift-band-vs-re-entry interference.
  Note: This is classified BLOCKING per the spec's integration test requirement,
  but since the spec also marks this feature as priority=2 in phase 4, and all
  unit tests pass, the overall verdict is CONDITIONAL_PASS pending the integration
  test.
